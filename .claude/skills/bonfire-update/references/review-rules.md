# 需求盘点

检查所有需求是否开发完成、还有哪些待完成，在开发文档目录下生成盘点文档和合并后的最终开发文档。

## 1. 何时执行

- 主版本更新（如 `0.x → 1.0.0`）时，在更新流程的测试与记录完成后执行。
- 用户要求：“盘点一下需求”“还有哪些功能没做完”“生成最终开发文档”。

## 2. 需求清单

基础是 `docs/project-spec.md` 的“需求清单”（`REQ-<三位序号>`，删除后不复用）：

| 编号 | 需求 | 来源 | 里程碑 | 对应功能 | 状态 | 备注 |
|---|---|---|---|---|---|---|

状态取值：待开发 / 开发中 / 已完成 / 推迟（原因与计划版本）/ 已取消（用户确认日期）。推迟或取消必须经用户同意。

## 3. 流程

1. **收集**：需求清单、待确认事项、里程碑与开发阶段；任务文档 `DevelopDocs/游戏存档备份软件 · 开发设计文档.md` 与相关文件；`docs/changelog/`；`bonfire-test` 的功能清单；`docs/acceptance/` 验收报告；代码中的 `TODO`、`FIXME`（只作线索）。
2. **核对每条需求**：已完成（实现且测试通过、满足验收标准）/ 已实现，未验证 / 部分完成（写明缺少部分）/ 未开始 / 推迟、已取消（沿用原因）。核对前询问是否运行全量测试（建议）/ 使用最近一次结果 / 不运行；不运行时没有最近结果的一律“已实现，未验证”。同时检查遗漏：任务文档或更新记录中有、清单里没有的需求补登记。
3. **与用户确认**：展示摘要（已完成数、新增功能数、待完成列表），对每条未完成需求询问：保留待开发 / 推迟到指定版本 / 取消（超过 4 条用编号列表批量回复）。确认后更新需求清单。
4. **生成文档**：`DevelopDocs/review/v<当前版本>_<日期>/`（同名已存在时加 `_2`、`_3`），文件名英文、内容中文，只新增不修改已有文件：
   - `completed.md`：按里程碑分组；需求编号、功能编号、名称、说明、完成版本、测试情况。
   - `added.md`：比较基准之后新增的功能（来源：用户反馈 U-xx、更新记录版本），没有时写“本次盘点无新增功能”。
   - `pending.md`：全部未完成需求（含推迟），写状态、缺少部分、原因、计划版本、依赖、优先级；末尾列“待确认事项”“已取消的需求”。
   - `TASK_merged.md`：以原任务文档为底并入全部变化的最终开发文档，结构沿用原文档章节；每条功能需求标注编号与状态（如“REQ-013 Linux 支持【推迟】”）；开头写合并基准，附录写变更来源；尽量保留用户原文。
5. **收尾**：在项目规范“开发文档”一节登记盘点目录（用途“盘点”）；询问是否把 `TASK_merged.md` 作为今后的任务文档（同意时原文档改为“相关文件（历史版本）”，文件本身不动）；汇报目录位置、各类数量与未完成需求的处理结果。

每份文档开头写：项目名称、当前版本、盘点日期、比较基准（上一次盘点目录；第一次为原始任务文档）。
