# 篝火 Bonfire · 开发设计文档

Oct 8, 2026 · @kun

## 1. 项目概述

本软件（中文名「篝火」，英文名 **Bonfire**）是一款桌面端游戏存档备份工具：自动扫描本机各平台的游戏存档，判断哪些有更新，由用户选择备份哪些，并以 Git 的快照模型保存完整历史，支持随时恢复到任意版本。

**目标**

- 覆盖 Steam、Epic、GOG、Ubisoft Connect、EA App、Xbox/Microsoft Store、Battle.net 及模拟器/独立游戏，开箱即用。
- 增量、去重存储：未变化的文件不重复占用空间。
- 每次备份（快照）可写备注，恢复前可预览差异，恢复操作本身可撤销。

**范围**：首版仅 Windows 10/11（64 位）；架构预留 Linux（Steam Deck/Proton）与 macOS。云同步、多设备合并列入后续版本，不在首版范围。

**术语**

| 术语 | 含义 | 对应 Git 概念 |
| --- | --- | --- |
| 游戏（Game） | 一个被识别的游戏条目，可含多个存档位置 | 仓库（repo） |
| 存档位置（SaveLocation） | 磁盘上的一个目录/文件通配或注册表键 | 工作区中的路径 |
| 快照（Snapshot） | 某一时刻一个游戏全部存档的完整状态 + 备注 | 提交（commit） |
| 对象（Blob） | 按内容哈希存储的文件内容 | blob |
| 清单（Tree） | 快照中的文件路径 → 对象哈希列表 | tree |
| 分支（Branch） | 一条快照线，如「主线」「二周目」 | branch |
| 标签（Tag） | 永久保留、不被清理的重要快照，如「Boss 前」 | tag |

## 2. 功能需求

首版功能共 10 项，其中 6 项 P0 为 MVP 必须交付。

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| F1 | 存档扫描 | 识别已安装的平台与游戏，定位存档路径；支持用户手动添加自定义游戏/路径；自动获取游戏名称、封面、开发商、游玩时长等信息（见 4.3） | P0 |
| F2 | 更新检测 | 对比当前磁盘状态与最近一次快照，标记「已修改 / 新增 / 已删除 / 未变化 / 从未备份」 | P0 |
| F3 | 选择性备份 | 列表勾选要备份的游戏（默认勾选有更新者），支持全选、反选、按平台筛选；可保存为「备份方案」复用 | P0 |
| F4 | 版本历史 | 每次备份生成一个快照；按游戏查看时间线、快照间文件差异；支持分支与标签 | P0 |
| F5 | 快照备注 | 备份时可为每个游戏的快照单独写备注；事后可修改；备注可搜索 | P0 |
| F6 | 存档恢复 | 恢复任意快照的全部或部分文件；恢复前自动为当前状态生成保护快照，可一键撤销 | P0 |
| F7 | 游戏运行保护 | 检测游戏进程在运行时警告或阻止恢复，避免存档被游戏覆盖 | P1 |
| F8 | 自动备份 | 定时扫描或游戏退出后自动备份，自动备注为「自动：退出游戏」 | P1 |
| F9 | 历史清理 | 保留策略（如保留最近 N 个 + 每天 1 个），标签快照永不清理；垃圾回收释放无引用对象 | P1 |
| F10 | 导入/导出 | 将单个游戏历史打包为单文件，用于迁移或分享 | P2 |

**关键约束**

- 备份和扫描对存档目录**只读**；只有恢复操作写入存档目录。
- 任何恢复都不得丢失数据：被覆盖的当前状态先入库。
- 仓库位置可配置（默认 `%LOCALAPPDATA%\Bonfire\repo`），可放在网盘同步目录中。

## 3. 系统架构

系统分为表现层、应用服务层、引擎层（存档发现 + 版本存储）和操作系统四层；GUI、CLI、后台守护共用同一套服务与引擎，引擎层不感知界面。

&#91;embedded content: 系统架构 · 4 层\]

只有恢复服务会写入存档目录，扫描与备份对存档目录只读。各模块职责如下：

| 模块 | 职责 | 关键依赖 |
| --- | --- | --- |
| 扫描服务 | 调用适配器与规则库得到存档位置，再做变更检测（第 5 节），输出每个游戏的状态 | 存档发现、SQLite 索引 |
| 备份服务 | 对用户勾选的游戏逐个读取文件、分块入库、生成快照并写入备注 | 对象库、Refs |
| 恢复服务 | 生成保护快照 → 进程检查 → 写回文件 → 记录操作，支持撤销 | 对象库、Refs、操作日志 |
| 历史服务 | 快照列表、差异对比、分支与标签管理、备注修改与搜索 | Refs、SQLite 索引 |
| 清理服务 | 执行保留策略、标记-清除垃圾回收、`fsck` 校验 | 对象库、Refs |
| 后台守护 | 监听游戏进程退出与定时器，触发自动备份 | 扫描服务、备份服务 |

## 4. 存档发现

存档发现采用「平台适配器 + 存档规则库」两层：适配器回答「装了哪些游戏、装在哪、用户 ID 是什么」，规则库回答「这个游戏的存档在哪」。

### 4.1 平台适配器

每个适配器实现统一接口：

```
interface PlatformAdapter {
  id: string                      // "steam" | "epic" | ...
  detect(): PlatformInfo | null   // 平台是否安装、安装目录
  listGames(): InstalledGame[]    // 已安装游戏：appId、名称、安装目录
  listUsers(): PlatformUser[]     // 本机登录过的账号 ID（用于路径变量）
  cloudSaveHint(appId): boolean   // 该游戏是否启用平台云存档
}
```

| 平台 | 游戏清单来源 | 存档常见位置 |
| --- | --- | --- |
| Steam | 注册表 `HKCU\Software\Valve\Steam` → `libraryfolders.vdf` → `appmanifest_*.acf` | `Steam\userdata\<steamId3>\<appId>\remote`、文档、AppData |
| Epic | `%ProgramData%\Epic\EpicGamesLauncher\Data\Manifests\*.item` | `%LOCALAPPDATA%\<Game>\Saved\SaveGames`（UE 游戏） |
| GOG Galaxy | `galaxy-2.0.db`（SQLite）或注册表 `HKLM\SOFTWARE\GOG.com\Games` | 文档、AppData |
| Ubisoft Connect | 注册表 `Ubisoft\Launcher\Installs` | `Ubisoft Game Launcher\savegames\<userId>\<gameId>` |
| EA App | `%ProgramData%\EA Desktop` 安装记录 | 文档、AppData |
| Xbox / MS Store | `Get-AppxPackage` 列表 | `%LOCALAPPDATA%\Packages\<PFN>\SystemAppData\wgs`（容器格式，只做整体备份） |
| Battle.net | `%ProgramData%\Battle.net\Agent\product.db` | 文档、AppData |
| 模拟器 / 独立游戏 | 用户手动添加 | 用户指定 |

### 4.2 存档规则库

规则库是一份按游戏列出存档路径模板的数据文件，有三个来源，优先级从高到低：

1. 用户自定义规则（本地、可覆盖任何内置规则）。
2. 社区规则库：建议直接复用 [Ludusavi Manifest](https://github.com/mtkennerly/ludusavi-manifest)（源自 PCGamingWiki，覆盖数万款游戏，YAML 格式），启动时增量更新。
3. 启发式探测：规则库没有的游戏，在常见目录中按游戏名/开发商名模糊匹配，结果标记为「待确认」，由用户确认后转为自定义规则。

规则示例：

```yaml
Elden Ring:
  platforms: { steam: { appId: 1245620 } }
  files:
    "<winAppData>/EldenRing/<storeUserId>/*.sl2": { tags: [save] }
    "<winAppData>/EldenRing/GraphicsConfig.xml": { tags: [config] }
  registry: []
```

**路径变量**：`<home>` `<winDocuments>` `<winAppData>` `<winLocalAppData>` `<winSavedGames>` `<base>`（游戏安装目录） `<root>`（库目录） `<storeUserId>`（平台用户 ID）。解析时展开变量，再用 glob 匹配实际文件。

**约定**

- 文件按 `save` / `config` 标签区分，用户可设置是否备份配置文件。
- 注册表存档导出为 `.reg` 文本后当作普通文件入库。
- 单个游戏存档超过阈值（默认 2 GB）时提示用户，防止误匹配到整个安装目录。

### 4.3 游戏信息自动获取

扫描到游戏后自动补全名称、封面、开发商、游玩时长等信息，用户无需手填。原则是本地数据优先、联网数据补充、结果全部缓存；获取失败或离线都不阻塞扫描和备份。

**字段与来源**（按优先级从高到低取第一个有值的）

| 字段 | 来源 |
| --- | --- |
| 名称（原名） | 平台本地清单（Steam `appmanifest` 的 name、Epic manifest 的 DisplayName、GOG 数据库）→ Steam Store API → IGDB |
| 中文名 | Steam Store API（语言参数为简体中文）→ IGDB 别名 → 用户填写 |
| 封面、竖版海报、横幅、图标 | Steam 本地 `appcache\librarycache` → Steam CDN 图片 → SteamGridDB → IGDB |
| 开发商、发行商、发行日期、类型 | Steam Store API（appdetails）→ IGDB |
| 游玩时长、最后游玩时间 | Steam `localconfig.vdf`；其他平台读启动器本地数据库；都没有时用存档最后修改时间代替 |
| 是否开启平台云存档 | Steam `remotecache.vdf` 等本地文件 |
| 外部 ID 映射 | Steam appId、IGDB id、SteamGridDB id、PCGamingWiki 页面名，用于后续精确查询和关联存档规则 |

**匹配策略**

1. 有平台 ID（Steam appId 等）时直接精确查询。
2. 无 ID 的游戏（手动添加、独立游戏）用可执行文件的产品名（PE 版本信息）或目录名，去掉版本号、符号后到 IGDB / SteamGridDB 搜索。
3. 搜索结果唯一且名称相似度高则自动采用，否则列出候选（含封面、年份）让用户选择；选定后写入外部 ID 映射，不再重复询问。
4. 用户可随时手动改名、换封面；手动修改的字段加锁，自动刷新不覆盖。

**接口设计**

```
interface MetadataProvider {
  id: string                                   // "steam-local" | "steam-store" | "igdb" | "sgdb" ...
  supports(game: Game): boolean
  fetch(game: Game, fields: Field[]): Partial<GameMetadata>
  search?(query: string): Candidate[]          // 无 ID 时的模糊搜索
}
```

`MetadataService` 按优先级链式调用各 Provider，合并结果并记录每个字段的来源。它属于应用服务层，由扫描服务在发现新游戏后异步触发。

**缓存与存储**

- 新增表 `game_metadata`：game\_id, name, name\_zh, developer, publisher, release\_date, genres\_json, cover\_path, icon\_path, hero\_path, playtime\_min, last\_played\_at, cloud\_save, external\_ids\_json, field\_sources\_json, locked\_fields\_json, fetched\_at。
- 图片存在 `cache/images/<gameId>/`，统一转为 WebP 并生成缩略图；缓存与存档仓库分开，删除后可重新下载。
- 文字信息有效期 30 天，过期后在后台增量刷新；游玩时长等本地字段每次扫描重读。
- 快照对象中另记录当时的游戏时长，便于在历史时间线上显示「已玩 42 小时时的存档」。

**联网与隐私**

- 请求走全局队列，按来源限速并退避重试；Steam Store API 无需 Key 但有频率限制。
- IGDB（需 Twitch 开发者凭证）和 SteamGridDB 需要 API Key：首版由用户在设置中填写，未填则跳过这两个来源；后续可提供官方代理服务。
- 只发送游戏 ID 或名称，不上传存档和账号信息；设置中可一键关闭所有联网获取。

## 5. 变更检测算法

变更检测采用 Git index 的做法：先用文件元数据快速筛选，元数据变化的文件再计算内容哈希确认，绝大多数未变化的文件无需读取内容。

**索引缓存（ScanIndex）**：每个游戏记录上次快照时每个文件的 `路径, 大小, mtime, 哈希`。

**单个文件判定**

1. 索引中无此路径 → **新增**。
2. 大小与 mtime 均未变 → **未变化**（不读内容）。
3. 任一变化 → 计算 BLAKE3 哈希；与索引哈希不同 → **已修改**，相同 → **未变化**（只更新索引中的 mtime）。
4. 索引中有、磁盘上无 → **已删除**。

**游戏级状态**：任一文件为新增/修改/删除 → 「有更新」；全部未变化 → 「已是最新」；从未快照 → 「未备份」。界面同时显示变化文件数、变化字节数和存档最后修改时间。

**细节**

- mtime 精度不一致（FAT32、网络盘为 2 秒）：mtime 与索引写入时间差小于 2 秒的文件一律重算哈希（同 Git 的 racy-git 处理）。
- 用户可触发「强制校验」，忽略元数据全量重算哈希。
- 哈希选 BLAKE3：多线程下显著快于 SHA-1/SHA-256，无已知碰撞问题。
- 扫描与哈希并行（线程池），按游戏逐个推送结果到界面，不等全部扫完。
- 备份时读取文件用共享读模式；若文件被游戏独占锁定，Windows 上可回退到 VSS 卷影复制读取（P2）。
- 实时监听（`ReadDirectoryChangesW` / inotify）仅用于自动备份触发，不替代上述对比。

## 6. Git 式版本存储模型

存储采用自研的类 Git 内容寻址仓库，而不是直接调用 git：存档多为二进制文件，Git 的文本 diff/merge 无用，而自研可以做分块去重、压缩、按游戏独立清理，且无需用户安装 git。概念上与 Git 一一对应，便于理解和实现。

### 6.1 仓库目录

```
repo/
├─ config.toml            # 仓库版本、压缩算法、分块参数
├─ objects/               # 内容寻址对象库（全局去重）
│   └─ ab/cdef0123...     # 前 2 位哈希为子目录，zstd 压缩
├─ packs/                 # GC 后小对象打包（P1）
├─ refs/
│   └─ <gameId>/
│       ├─ heads/main     # 分支指针 → 快照哈希
│       ├─ heads/ng-plus
│       ├─ tags/before-boss
│       └─ HEAD           # 当前分支名
├─ notes/<snapshotHash>   # 备注修改记录（见 6.3）
├─ logs/<gameId>.jsonl    # 引用变更日志（reflog），用于找回和撤销
└─ bonfire.db           # SQLite：元数据索引（可从 objects/refs 重建）
```

### 6.2 对象类型

| 对象 | 内容 | 哈希计算 |
| --- | --- | --- |
| Chunk | 文件内容的一个分块（zstd 压缩） | BLAKE3(原始字节) |
| Blob | 一个文件：大小 + 有序 Chunk 哈希列表；小文件（< 1 MB）只有一个 Chunk | BLAKE3(整个文件) |
| Tree | 一个快照内所有文件：相对路径（带存档位置前缀）、Blob 哈希、大小、mtime、标签 | BLAKE3(规范化 JSON) |
| Snapshot | Tree 哈希、父快照哈希列表、时间、触发方式（手动/自动/恢复前保护）、机器名、备注 | BLAKE3(规范化 JSON) |

**分块去重**：大文件用内容定义分块（FastCDC，平均 1 MB）。很多游戏每次只改存档的一小部分，分块后每次只新增变化的块。加密或整体压缩的存档分块无效，退化为整文件去重，仍正确。

### 6.3 备注存放

备注写入 Snapshot 对象，但事后修改不重写快照（否则哈希变化、子快照的父链断裂）。修改后的备注存为独立的「注记」（对应 `git notes`）：`notes/<snapshotHash>` 保存当前备注及修改历史，显示时优先取注记。

### 6.4 分支与标签

- 每个游戏独立一组 refs，默认分支 `main`。
- 从旧快照恢复后继续游玩，下次备份时快照的父节点是被恢复的快照。软件询问：「创建新分支」（保留原主线）或「移动当前分支」（原主线后续快照变为无分支指向，但仍由 reflog 保留 30 天）。默认创建新分支。
- 存档无法合并，不提供 merge；分支只用于保留平行进度（多周目、不同结局线）。
- 标签为不可移动的命名指针，受保护不被自动清理。

### 6.5 写入一致性

写入顺序固定为 Chunk → Blob → Tree → Snapshot → 更新 ref。每个对象先写临时文件再原子重命名；ref 更新是最后一步，崩溃只会留下无引用对象，由 GC 清理，不会出现半个快照。仓库用文件锁防止多实例同时写入。

### 6.6 清理与垃圾回收

保留策略先决定删哪些快照（从分支历史中「压掉」：子快照的父指针改指向保留的祖先，类似 rebase），再从所有 ref 与 30 天内 reflog 出发做标记-清除，删除未被引用的对象。

## 7. 数据结构与数据库设计

对象库与 refs 是唯一事实来源；SQLite （`bonfire.db`）只存游戏配置与加速查询的索引，损坏后可由「重建索引」命令从对象库恢复（游戏配置另存 `games.toml` 备份）。

### 7.1 快照对象（JSON）

```json
{
  "type": "snapshot",
  "game": "steam-1245620",
  "tree": "b3:9f1c...",
  "parents": ["b3:77ae..."],
  "createdAt": "2026-10-08T21:14:03+08:00",
  "trigger": "manual",          // manual | auto-exit | auto-timer | pre-restore
  "host": "DESKTOP-01",
  "comment": "打完大树守卫，强化 +5 前",
  "stats": { "files": 12, "bytes": 48213504, "changed": 2 }
}
```

### 7.2 SQLite 表

| 表 | 主要字段 | 用途 |
| --- | --- | --- |
| `games` | id, name, platform, app\_id, install\_dir, enabled, include\_config, custom\_rule\_json | 已识别或手动添加的游戏及其设置；游戏信息另存 game\_metadata 表（见 4.3） |
| `save_locations` | id, game\_id, path\_template, resolved\_path, kind（file/dir/registry）, tag（save/config）, source（manifest/user/heuristic）, confirmed | 游戏的存档位置 |
| `scan_index` | game\_id, rel\_path, size, mtime\_ns, hash, indexed\_at | 变更检测缓存（见第 5 节） |
| `snapshots` | hash, game\_id, created\_at, trigger, comment, files, bytes, changed | 快照列表索引，支持分页、按备注全文搜索（FTS5） |
| `snapshot_parents` | snapshot\_hash, parent\_hash, ord | 历史图遍历 |
| `refs` | game\_id, name, kind（branch/tag）, target\_hash, updated\_at | refs 镜像，启动时与文件校对 |
| `backup_profiles` | id, name, game\_ids\_json, default\_comment | 「备份方案」：一组常用的游戏选择 |
| `operations` | id, kind（backup/restore/gc）, started\_at, finished\_at, status, detail\_json | 操作日志，供「撤销上次恢复」和排错 |

### 7.3 游戏 ID 规则

`<platform>-<appId>`，如 `steam-1245620`、`epic-<catalogItemId>`；手动添加的为 `custom-<uuid>`。同一游戏在两个平台各有一份时视为两个游戏，可由用户手动关联。

## 8. 核心流程

备份和恢复都是「先写对象、最后动指针」，任何一步失败都不会破坏已有历史或当前存档。

&#91;embedded content: 备份与恢复流程\]

### 8.1 备份

1. 扫描并检测变更，列表默认勾选「有更新」和「未备份」的游戏。
2. 用户调整勾选（或选择备份方案）后点「备份所选」。
3. 确认弹窗中为每个游戏单独填写备注；留空则自动生成（如「修改 2 个文件，+3.1 MB」）。
4. 逐个游戏执行：读文件 → 分块 → 已存在的 Chunk 跳过 → 写入新 Chunk/Blob → 写 Tree → 写 Snapshot。
5. 一个游戏的快照写完后立即更新其当前分支指针和 reflog，并更新 ScanIndex。单个游戏失败不影响其他游戏，结束后汇总显示。
6. 若与上一快照的 Tree 哈希相同（无实际变化），默认不生成新快照；用户勾选「强制快照」可用于仅打备注或标签。

### 8.2 恢复

1. 在历史页选中快照，可勾选部分文件（如只恢复某个存档位）。
2. 预览与当前磁盘的差异：将覆盖、将新增、将删除的文件。删除仅在「完全恢复」模式下发生，默认只覆盖不删除。
3. 检测游戏进程（从安装目录匹配可执行文件），运行中则提示关闭。
4. 若当前磁盘状态与最新快照不同，先生成触发方式为 `pre-restore` 的保护快照，备注自动为「恢复到 <目标> 前的自动保护」。
5. 将文件写入存档目录旁的临时文件，全部成功后逐个原子替换；中途失败则用保护快照回滚。
6. 记录到 `operations` 表，并将 HEAD 标记为「已从 X 恢复」，下次备份时触发分支选择（见 6.4）。「撤销恢复」即恢复保护快照。

### 8.3 备注

- 备份时：在确认弹窗中逐游戏填写，支持一键统一填充。
- 事后修改：历史页双击备注编辑，写入 notes（见 6.3），保留修改历史。
- 搜索：备注进入 SQLite FTS5 全文索引，可跨游戏搜索。
- 长度上限 500 字；第一行作为时间线上的摘要显示。

## 9. UI 设计与 CLI

桌面端为主，共 4 个主页面；另提供与 GUI 共用核心库的 CLI，便于脚本和计划任务调用。

### 9.1 页面

| 页面 | 内容 | 主要操作 |
| --- | --- | --- |
| 游戏库（首页） | 游戏列表：封面、名称、平台图标、状态徽标（有更新/已是最新/未备份/待确认）、变化文件数、最后备份时间、历史占用空间 | 扫描、勾选、按平台/状态筛选、选择备份方案、「备份所选」 |
| 备份确认弹窗 | 所选游戏逐行列出，每行一个备注输入框 + 可展开的变化文件列表；顶部「统一备注」可一键填充所有行 | 确认、改单个备注、勾选「同时打标签」 |
| 游戏详情 / 历史 | 左侧分支与标签；中间快照时间线（按分支绘制图，每个节点显示时间、备注、触发方式图标）；右侧选中快照的文件列表及与当前磁盘或上一快照的差异 | 恢复、部分恢复、编辑备注、打标签、建分支、导出、搜索备注 |
| 设置 | 仓库位置、平台开关、是否备份配置文件、自动备份、保留策略、规则库更新、游戏信息来源与 API Key、自定义游戏管理 | 保存、立即清理、校验仓库、重建索引 |

**交互要点**

- 恢复确认弹窗必须显示：将覆盖的文件、将删除的文件、已自动创建的保护快照。
- 恢复完成后顶部常驻「撤销本次恢复」提示，直至下一次备份。
- 开启平台云存档的游戏恢复前提示：需在启动游戏时选择「保留本地存档」，否则可能被云端覆盖。
- 长任务（扫描、备份、GC）在后台执行，显示进度与可取消按钮；系统托盘常驻用于自动备份。

### 9.2 CLI

```
bonfire scan [--platform steam] [--json]
bonfire status [<game>]
bonfire info <game> [--refresh]
bonfire backup <game>... [-m "备注"] [--profile <name>] [--tag <name>]
bonfire log <game> [--branch <b>] [--grep <备注关键词>]
bonfire diff <game> <snapA> [<snapB>]
```

## 10. 非功能需求、技术选型、风险与里程碑

### 10.1 非功能需求

| 类别 | 指标 |
| --- | --- |
| 扫描性能 | 200 款游戏、无变化时增量扫描 < 3 秒（SSD）；首次全量扫描 < 30 秒 |
| 备份性能 | 哈希 + 压缩吞吐 ≥ 200 MB/s（多线程） |
| 存储效率 | 未变化文件零新增存储；快照元数据每个 < 10 KB |
| 可靠性 | 任意时刻断电不损坏已有快照；`fsck` 可校验所有对象哈希 |
| 安全 | 不联网上传任何存档；仅规则库更新联网；仓库可选 AES-256-GCM 加密（P2） |
| 资源占用 | 托盘常驻内存 < 80 MB；自动备份在游戏运行中不做重 IO |
| 兼容 | 仓库格式带版本号，新版本软件可读旧仓库 |

### 10.2 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 核心库 | Rust | 文件 IO 与并发性能好；`blake3`、`zstd`、`fastcdc`、`rusqlite`、`globset` 等 crate 成熟 |
| 桌面 UI | Tauri 2 + React/TypeScript | 安装包小（约 10 MB），直接调用 Rust 核心库 |
| CLI | Rust + `clap` | 与 GUI 共用核心库 |
| 规则库 | Ludusavi Manifest（YAML） | 现成且持续维护的社区数据 |

备选：若团队更熟悉 .NET，可用 C# + WPF/Avalonia 实现，数据模型不变。

### 10.3 风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 存档路径识别不全或误匹配 | 漏备份或备份大量无关文件 | 规则库 + 用户确认机制；大小阈值告警；提供「提交规则」入口 |
| 平台云存档覆盖已恢复存档 | 恢复「失效」 | 恢复前提示；恢复后将文件 mtime 设为当前时间，使平台判定本地更新 |
| 游戏运行中写入存档 | 备份到半写状态、恢复被覆盖 | 进程检测（F7）；备份后复核 mtime，变化则重试 |
| Xbox/Game Pass 容器存档 | 无法按文件粒度处理 | 整个 `wgs` 目录作为单元备份/恢复 |
| 反作弊或存档绑定账号/机器 | 跨机恢复失败 | 快照记录机器名与用户 ID，跨机恢复时提示 |
| 仓库所在盘损坏 | 历史丢失 | 建议仓库放在非系统盘或同步盘；定期 `fsck` |

### 10.4 里程碑

1. **M1 核心库**：对象库、快照、refs、变更检测、恢复与撤销；只支持手动添加路径；CLI 可用。验收：随机断电测试无快照损坏。
2. **M2 存档发现**：Steam、Epic、GOG 适配器 + Ludusavi 规则库接入。验收：测试机上 50 款常见游戏识别率 ≥ 90%。
3. **M3 GUI MVP**：游戏库、备份确认（含逐个备注）、历史时间线、恢复。P0 全部交付。
4. **M4 完善**：其余平台适配器、自动备份、保留策略与 GC、运行保护（P1）。
5. **M5 扩展**：导入导出、加密、VSS、Linux/Steam Deck 支持（P2）。
